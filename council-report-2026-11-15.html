Chairman's recommendation. One Node process. Headless-first job-runner core (task queue → SQLite WAL → sandboxed tool executor → event log); the Canvas 2D world is a client view over WebSocket. No Phaser, no Chromium, no Docker. Single model slot — start with qwen2.5:1.5b-instruct-q4_K_M, structured output (format JSON schema) ON, model swappable via config. Watchdog lives outside the app (Task Scheduler). Security floor day one: path whitelist, shell whitelist, kill switch, step/token budgets, event-log rotation. Setup is part of the product.

Where the Council Agrees

  • One model slot, one inference at a time — 4 advisors converged independently; turn-taking is mandatory and more believable.
  • Drop Phaser → pure Canvas 2D — smaller, no WebGL pressure on shared iGPU, no dependency tax.
  • Event-driven cognition, never continuous loops — biggest lever on idle CPU and thermals.
  • SQLite WAL via better-sqlite3 — 24/7 write safety; JSON files corrupt.
  • Headless job runner is the core; world is a view — 24/7, recovery, idle power fall out for free.
  • Crash recovery outside the process — Task Scheduler / .bat watchdog.
  • Single Node process — Express + ws + better-sqlite3 + Ollama HTTP API. No Docker, no microservices.

Where the Council Clashes

Model class: 1.5B workhorse vs 3B minimum. B/E optimize for RAM fit; D for tool-call capability. Resolution: Ollama structured output forces schema-valid tool calls by construction — moves most of D's failure from "model problem" to "solved constraint." Make the model a config entry; measure on real hardware; swap to 3B if needed (budget has room for exactly one swap). Never two models resident.

Blind Spots the Council Caught

  • Constrained decoding (structured output with JSON schema) — nobody's advisor proposed it; likely settles the model-class fight.
  • Windows power policy — sleep/hibernate kills 24/7 before software does; disabling sleep on AC is a required setup step.
  • Thermal throttling — unanimous among reviewers; num_thread to 4 physical cores; fanless-class tablet under sustained load.
  • First-run UX — SmartScreen, memory dialogs, model download progress will trip the target user; walk the first error in the docs.
  • Security / kill switch — 24/7 autonomous shell access on a personal machine needs path + command whitelists and a kill switch.
  • Context budget — memory injection must be ranked + truncated, never dumped.
  • Event-log growth — rotation needed on a 256 GB drive.
  • Web research fragility — cache results, degrade offline.
  • Measurement discipline — every RAM/latency number was asserted, none measured.

Advisor Full Responses

The Expansionist (A)
Event-driven architecture over polling — batch and queue agent cognition; LLM fires only at decision points. Package the headless scheduler + tool protocol as an open-source core. The world is the UI: keep renderer and runtime strictly separated over WebSocket — a reusable "embodied agent viewer." Skills folder = marketplace seed; publish the manifest format. Crash recovery + 24/7 headless = a lightweight autonomous-agent harness module. Pick: Phaser 3 yes, bet on 0.5B-class models + SQLite WAL + "cognition is scheduled, not continuous."
The Outsider (B)
8 GB is the whole project; Ollama with 3–5 agents is where it dies. Windows eats 2.5–3 GB first. Subtraction: one model at a time, all agents queue; 0.5B–1.5B only; don't run Ollama 24/7 (keep-alive=0 or sleep the process); kill the browser — WebView2 native window, not Chromium or Electron; SQLite not JSON; watchdog outside the app (Task Scheduler + restart script).
The First Principles Thinker (C)
Wrong question. Real question: how much inference can 8 GB sustain, and how do we architect so the AI almost never runs? One small model. Agents are event-driven state machines that occasionally ask the model a question. Invert: headless job runner (queue → SQLite WAL → sandboxed tool executor → event log) is the core; the world is a client view. Kill Phaser (~1,500 lines Canvas). Production-ready = single Node process, .bat watchdog, OLLAMA_NUM_PARALLEL=1, capped context. The queue and tool protocol are the product; the office is marketing.
The Contrarian (D)
Fatal flaw: 0.5B–2B models can't reliably emit tool calls (malformed JSON, hallucinated paths). Budget one 3B-class model (qwen2.5-3b Q4 ≈ 1.9 GB), one agent thinking at a time. Memory math doesn't close with a browser renderer; headless 24/7 shouldn't run the game loop. Cold-load is 10–30 s. Never `vite dev` 24/7 — static build + lightweight server. Concrete fix: Canvas 2D, schema-validated whitelisted tool protocol, one model/one slot/queue. If 3B doesn't fit, be honest in docs that 1.5B writes summaries, not production code.
The Executor (E)
Drop Phaser (60-line A*, vanilla TS). ONE Node process: Express + ws + better-sqlite3 (sync API). Model: qwen2.5:1.5b-instruct-q4_K_M default, one slot enforced. Tool protocol = Ollama native tool calling: read_file, write_file, run_shell (whitelisted), web_fetch (DuckDuckGo). While-loop with step cap + token cap. Day-one failure modes: agent loops, Ollama crash, idle CPU burn (30fps visible / halt headless; agents on timers, not game loop). Setup = winget + ollama pull + start.bat.

Peer Review Highlights

  • R1: Strongest D (attacked load-bearing premise); flagged structured output as the dispute-solver; all numbers asserted, none measured.
  • R2: Strongest E (only Monday-morning artifact); D self-contradicts on persistence; flagged thermals, first-run UX, state migration.
  • R3: Strongest B (binding constraint + decisive calls); merge B with C; flagged power reality, security, log growth, measurement-first spike.
  • R4: Strongest C (inversion solves 24/7 as side effect); D undated overconfidence; flagged setup failure UX, context budget, Windows sleep policy.
  • R5: Strongest E (buildable plan); A never engages hardware math; flagged thermals, run_shell sandbox, web research fragility.
The one thing to do first: a two-hour spike on the actual Surface Pro 6, headless — Ollama + qwen2.5:1.5b-instruct-q4_K_M, 20-call loop under a JSON tool-call schema via format, execute each call, record success rate / latency / peak memory with keep-alive off. ≥80% valid-executable tool calls → architecture settled at 1.5B; below → one-line config swap to 3B knowing the budget survives it.
